# OKR 周报写作规范

作者：Xuyiming。依据用户提供的周报风格提炼；下列技术场景是写法示例，不是本周事实。

## 正文结构

标题写明实际统计日期，例如 `周报 OKR｜2026-09-21—2026-09-27`，附一行说明“上一完整自然周，按提交者时间筛选本人作者邮箱；仅本地已同步历史”。如果没有配置当前目标，标题注明“建议 OKR 草稿”，目标不虚构验收阈值。

每个目标保持原始 `【诺】` / `【愿】` 和措辞；有完整 O/KR 层级时保留，不将 O 和 KR 混成重复成果。目标下固定四段，每段通常 1—3 句：

```text
【诺】高质量、按期完成业务需求交付，保障版本稳定上线
本周进展：
围绕直播间进房链路完成资源复用与控件按需创建等代码调整，相关变更已提交；当前证据未覆盖统一送测与验收结果。
发现的问题：
尚缺关键场景回归记录，现有提交不足以确认交付验收完成。
风险同步与资源支持：
建议结合测试排期覆盖冷启动进房、重复进退房和上下麦场景，确认时序及资源释放边界。
下周进度计划：
建议补齐上述场景验证并整理送测范围，具体排期需确认。
```

示例必须替换为实际证据支持的主题；不要将资源复用、RTC、特定组件等写成每周必备事项。

## 提炼规则

- 写业务目的、实际动作、当前阶段和下一步，不粘贴 commit 清单；同一优化跨组件可合并为一条主题。
- 范例中重复粘贴的段落只学习一次，不在成品里重复输出。
- 区分分析定位、实现提交、编译测试、发布上线、业务验收。没有独立证据就停在已证实阶段。
- 指标必须注明来源和边界。少量设备采样不能代表全部设备；测试数量不能代替交付率、事故数或代码质量评分。
- 若发生回滚，表述实际回滚及截至统计周期结束的状态，不把被撤销功能算作完成。后续新周修复可作为明确标注的补充，不计入上周新增成果。
- 未完成事项不能仅从代码里出现 `TODO` 推断；结合改动和上下文，不把缺少验收证据误报为功能故障。
- 与当前目标无关的提交单列“其他工作”，不要硬塞。目标没有匹配提交时写“本期采集范围内暂无新增可核验进展”，不是“没有工作”。
- 没有具体问题证据时写“暂未从本周提交中确认新增问题，仍需结合测试和业务反馈核实”；不编造阻塞。
- 风险写真实依赖或明确的验证缺口；下周计划依据遗留事项给出建议，未知安排写“需结合排期确认”，不冒充已承诺事项。
- 不假定持续监控已经在进行，不把样例里的监控承诺或旧月份自动延续。

## 证据附录与交付自检

正文后增加简短附录：周期、作者邮箱、扫描根目录、排除规则、实际仓库数量、未完成采集范围；每项主题列仓库名、短 SHA 与已确认的动作。需要追溯时链接本地证据 JSON；不要在正文堆积全量提交。

交付前检查：有无把他人提交计入本人；有无重复计算相同业务；有无将作者自述包装为独立验证；有无未经证明的“已推送/已上线/100%/0 BUG”；有无继承示例旧月份、指标和数值；有无把建议计划当作用户承诺。证据不足时保留不确定性，不用漂亮措辞掩盖。
